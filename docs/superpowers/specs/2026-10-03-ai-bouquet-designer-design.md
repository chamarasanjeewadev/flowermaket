# AI Bouquet Designer — Design Spec

**Date:** 2026-10-03  
**Status:** Draft — awaiting user review before implementation planning

---

## Overview

A standalone, bilingual, SEO-indexable page at `/$locale/design` where a buyer picks individual flowers (by stem, with quantities) from the live catalog, generates a photo-realistic AI preview of the resulting bouquet, and sends the selection as a WhatsApp enquiry to the marketplace. The page is lead-generating: the "wow" of an AI visualization funnels into the existing WhatsApp enquiry basket, which florists already answer.

The AI image is generated by Google's Imagen (Gemini Generative Language API) via raw `fetch` from a TanStack Start server function — Workers-safe, no SDK, mirroring the validated `cloudinary-devs/ai-bouquet-generator` reference pattern. The feature **fails soft**: if the Gemini key is absent or the API errors, the picker and WhatsApp enquiry still work end to end.

This reuses three existing subsystems unchanged: the catalog query layer (`listProducts` / repo in `@flowers/api`), the WhatsApp enquiry basket (`lib/enquiry.tsx` + `@flowers/integrations`), and the lazy-env pattern (`getEnv()`).

---

## 1. Architecture

New route: `apps/web/src/routes/$locale/design.tsx` — **indexable** (full meta + `hreflang` + JSON-LD), unlike the `noindex` `/enquiry` utility page.

Four units, each independently testable:

| Unit | Path | Responsibility |
|---|---|---|
| Route | `apps/web/src/routes/$locale/design.tsx` | Loader fetches designable flowers; `head` emits SEO; renders `BouquetDesigner`. |
| UI: orchestrator | `apps/web/src/components/design/BouquetDesigner.tsx` | Owns selection state (`EnquiryItem[]`), wires picker ↔ preview ↔ WhatsApp. |
| UI: picker | `apps/web/src/components/design/FlowerPicker.tsx` | Catalog grid + per-flower quantity steppers. |
| UI: preview | `apps/web/src/components/design/BouquetPreview.tsx` | Generated image, loading/error states, Download + Send-via-WhatsApp actions. |
| Server fn | `apps/web/src/server/bouquet.ts` | `generateBouquetImage({ items })` — lazy `getEnv()`, builds prompt, calls Gemini, returns base64 data URL. |
| Pure prompt builder | `packages/integrations/src/bouquet.ts` | `buildBouquetPrompt(items, locale)` — unit-testable, no I/O. |
| Catalog query | `packages/api/src/repos/catalog.ts` (new fn) | `listDesignerFlowers(db)` — pulls across the configured flower-category slug set. |

Data flow:

```
loader → listDesignerFlowers() ─────────────► FlowerPicker (grid)
                                                   │ pick + qty (client state: EnquiryItem[])
                                                   ▼
                                           BouquetDesigner
                                     ┌─────────────┴─────────────┐
                            generateBouquetImage({items})   add() each item → basket
                                     │                            │
                              buildBouquetPrompt              buildEnquiryText
                                     │                            │
                              Gemini (fetch)                 buildWhatsappUrl → wa.me/94778540633
                                     ▼
                              BouquetPreview (image + Download)
```

## 2. Catalog & picker

### 2.1 Designable-flower source — configured category set

The real single-stem products live across **four type-specific categories** (`roses`, `gerberas`, `orchids`, `chrysanthemums`), all `listingType: "wholesale"` with per-stem MOQs (25–100). The seed's `loose-flowers` category exists but is unpopulated. Because a product has a single `category_id` FK, the designer sources flowers from a **configured slug set** rather than one category.

New constant in `@flowers/api` (alongside `CATALOG_PAGE_SIZE`):

```ts
export const DESIGNER_CATEGORY_SLUGS = [
  "roses",
  "gerberas",
  "orchids",
  "chrysanthemums",
  "loose-flowers",
] as const;
```

New repo query in `packages/api/src/repos/catalog.ts`:

```ts
export function listDesignerFlowers(db: Db): Promise<ProductListItem[]>
```

- Reuses the existing `publicConditions()` (active/public products only).
- Filters `categories.slug IN DESIGNER_CATEGORY_SLUGS` (Drizzle `inArray`).
- Returns the same `ProductListItem` shape the browse grid uses (id, slug, nameEn/Si, price, listingType, primary image storage path, etc.) — so image resolution reuses `resolveImageUrl()` unchanged.
- No pagination (the designable set is small and bounded); ordered by category `sortOrder` then product `nameEn`.

New server function in `apps/web/src/server/catalog.ts` (co-located with the existing catalog server functions; `generateBouquetImage` lives separately in `server/bouquet.ts`):

```ts
export const listDesignerFlowers = createServerFn(...).handler(async () => {
  const db = tryCreateDb();
  if (!db) return { items: [] };
  // setPublicCatalogCache()
  return { items: (await repoListDesignerFlowers(db)).map(toListItemDTO) };
});
```

On DB error → returns `{ items: [] }` (matches existing `listProducts` fail-soft behavior).

### 2.2 Picker UI

`FlowerPicker` renders `ProductListItemDTO[]` as a responsive grid of cards: resolved image, bilingual name (via `useT()`), price, and a quantity stepper (0 → N). Selection state lives in `BouquetDesigner` as `EnquiryItem[]` from the first pick — no mapping needed when it later enters the enquiry basket. A running summary ("3 flowers, 11 stems") and a prominent **Generate** button (disabled while selection is empty).

The wholesale `listingType` carries through to the enquiry item; MOQ is **not enforced at design time** — this is a visualization + enquiry tool, and the florist quotes against the enquiry. (A later enhancement could surface MOQ hints in the picker.)

## 3. AI generation

### 3.1 Prompt builder (pure, testable)

`packages/integrations/src/bouquet.ts`:

```ts
export interface BouquetPromptItem {
  nameEn: string;
  qty: number;
}
export function buildBouquetPrompt(
  items: readonly BouquetPromptItem[],
  locale: "en" | "si",
): string
```

- Always uses the **English** flower names for the prompt (Imagen prompting is English-only; locale is accepted for future tuning / negative-prompt copy but does not switch the flower vocabulary).
- Produces a deterministic string, e.g.:
  > `A photorealistic professional florist bouquet containing 5 red roses, 3 white lilies, and 2 pink gerberas, hand-tied and wrapped in kraft paper, soft natural studio lighting, clean neutral background, high detail, no text, no watermark.`
- Pure and side-effect-free → unit-tested identically to `buildEnquiryText`.

### 3.2 Image generation server function

`apps/web/src/server/bouquet.ts`:

```ts
export const generateBouquetImage = createServerFn(...)
  .validator((d: { items: BouquetPromptItem[] }) => d)
  .handler(async ({ data }) => {
    const { GEMINI_API_KEY } = getEnv();               // lazy — inside handler
    if (!GEMINI_API_KEY) return { ok: false as const, reason: "unconfigured" };
    if (data.items.length === 0) return { ok: false as const, reason: "empty" };

    const prompt = buildBouquetPrompt(data.items, "en");
    try {
      const res = await fetch(IMAGEN_ENDPOINT + `?key=${GEMINI_API_KEY}`, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify(imagenRequestBody(prompt)),
      });
      if (!res.ok) return { ok: false as const, reason: "api_error" };
      const b64 = extractImageBase64(await res.json());
      if (!b64) return { ok: false as const, reason: "api_error" };
      return { ok: true as const, dataUrl: `data:image/png;base64,${b64}` };
    } catch {
      return { ok: false as const, reason: "api_error" };
    }
  });
```

- Model: Imagen on the Generative Language API (`imagen-3.0-generate-*` via `:predict`, or the current Gemini image-generation model) — exact endpoint/body confirmed during implementation against the reference repo; isolated in `imagenRequestBody()` / `extractImageBase64()` helpers so the model can be swapped without touching callers.
- **Returns a base64 data URL inline** — no Supabase storage in v1 (stateless, no new bucket/RLS). Persisted shareable URLs are a noted future enhancement.
- Never throws to the client; always returns a discriminated result (`ok: true | false` with a typed `reason`).

### 3.3 Env

Add to `packages/api/src/env.ts`:
- `AppEnv`: `GEMINI_API_KEY: string | undefined;`
- `getEnv()` return: `GEMINI_API_KEY: read("GEMINI_API_KEY"),`

Set as a Cloudflare secret for `apps/web` (and in `apps/web/.dev.vars` for local dev, per the "dev vars for local DB" convention). Absence disables generation gracefully.

## 4. WhatsApp enquiry

"Send via WhatsApp" in `BouquetPreview` reuses the basket end to end:

1. For each selected flower, call `useEnquiry().add(item)` (items are already `EnquiryItem`-shaped).
2. Build the message with the existing `buildEnquiryText({ items, locale, siteUrl })` and open `buildWhatsappUrl(text)` → `https://wa.me/94778540633?text=...`.

The itemized list, quantities, "(Wholesale)" labels, and per-product links all come free from `buildEnquiryText`. Because a `wa.me` text link cannot carry an image, `buildBouquetPrompt`'s nature means the message is fully descriptive (flower list + quantities); `BouquetPreview` offers a **Download** button so the buyer can attach the AI preview image in the chat. The florist thus receives both the exact flower list and the visual.

**Small integration decision:** the enquiry text gains an optional leading line noting an AI bouquet design was created (e.g. "— AI bouquet design (image attached) —"). Implemented via an optional field on `BuildEnquiryTextInput` so the existing `/enquiry` and FAB flows are unaffected. (If preferred, this can be dropped to keep `@flowers/integrations` untouched — flagged for review.)

The existing `FloatingWhatsApp` FAB automatically reflects designer-added items (it reads the same `useEnquiry()` store) with no change.

### 4.1 WhatsApp number → single config file

The marketplace WhatsApp number is currently a constant buried in `packages/integrations/src/whatsapp.ts` (`WHATSAPP_NUMBER = "94778540633"`). Extract it to a dedicated config module as the **single source of truth**, editable in one place:

- New file `packages/integrations/src/config.ts` exporting `export const WHATSAPP_NUMBER = "94778540633";` (plus room for future marketplace constants).
- Re-export from the package index (`packages/integrations/src/index.ts`).
- `whatsapp.ts` imports it; `buildWhatsappUrl(text, numberDigits = WHATSAPP_NUMBER)` default references the config value.
- All call sites (FAB, `/enquiry`, designer) go through `buildWhatsappUrl`, so no call site hardcodes the number — changing `config.ts` changes it everywhere.

## 5. Error handling (fail-soft)

| Condition | Behavior |
|---|---|
| No `GEMINI_API_KEY` | Generation UI hidden/disabled with a short note; **picker + WhatsApp fully functional.** |
| Gemini API error / non-200 / timeout | Friendly inline error in `BouquetPreview`; selection preserved; WhatsApp still works. Server fn returns `{ ok: false, reason: "api_error" }`. |
| Empty selection | Generate button disabled; server fn also guards (`reason: "empty"`). |
| Catalog DB error | Empty grid (consistent with `listProducts`). |
| Abuse / cost | v1: client-side debounce + Generate disabled while a request is in flight. **Server-side rate-limiting is a documented fast-follow** — a public image-gen endpoint incurs real per-call cost (~$0.03–0.04/image). |
